# 语音转写服务 — 操作说明

本文说明：服务干什么、怎么部署、怎么从公司内网调用、怎么看日志/结果、怎么压测与排障。

---

## 1. 这是什么、谁调用谁

| 角色 | 机器 | 职责 |
|------|------|------|
| 业务流水线 | 公司内网 **CPU** 机器 | 剪辑/业务主流程；需要转写时发 HTTP 请求 |
| 本服务 | **AutoDL（GPU）** | 接收音频、排队、用 Whisper 转写、返回文本与时间戳 |

**访问的「服务」= AutoDL 上这个语音转写 HTTP 接口**，不是公司内别的系统。

数据约定：

- **上传的音视频**：推理结束立刻删除，不长期存。
- **转写结果文档**：写入 `asr_server/results/{task_id}.json`，**默认保留 24 小时**，到期自动删。
- **日志**：每次启动单独一个目录，`asr_server/logs/年-月-日/时-分-秒/`。里面是这次启动的 `asr.log`（业务）和 `stdout.log`（控制台）。同一秒再启动会加成 `时-分-秒-2`。默认保留 3 天。每条任务一行【开始】、一行【结束】，【结束】里是完整返回，包含转写全文。

并发约定：

- 内网可以一口气提交几十到上百个任务（排队上限默认 200）。
- 服务先把任务放进队列，再分给空闲的转写路。每一路单独占一个进程、一份模型，一次只做一条。
- 路数写在 `asr_server/service.conf` 的 `workers`，默认 `2`。改完要重启。本机最多按 `3` 路启动。

## 2. AutoDL 上：准备环境

### 2.1 依赖（本机已验证过可跳过）

- Conda 环境：`whisper-turbo`
- 已安装：`openai-whisper`、`torch`（CUDA）、`ffmpeg`、`fastapi`、`uvicorn`、`python-multipart`、`httpx`
- 模型权重目录（默认）：`/root/autodl-tmp/models/whisper`（含 `large-v3-turbo.pt`）

若需补装 Python 包：

```bash
/root/miniconda3/envs/whisper-turbo/bin/pip install -r requirements.txt
```

### 2.2 设置密钥（上线必做）

```bash
# 生成示例（任选一种足够长的随机串）
openssl rand -hex 32

export ASR_API_KEY='01d503268439d1d4647edb144925724029dc93370d13bd52a1f8e70c6f8a49fa'
```

建议把 `export ASR_API_KEY=...` 写进开机脚本或 AutoDL 启动命令，避免每次手敲。

未设置密钥时服务也能启动，但**任何人可达即可调用**，内网打 AutoDL 公网端口时非常危险。

### 2.3 启动服务

```bash
cd /root/autodl-tmp/video_cut_forigen
export ASR_API_KEY='你的密钥'
bash scripts/start_asr.sh
```

默认监听：`0.0.0.0:6006`。

后台运行示例：

```bash
cd /root/autodl-tmp/video_cut_forigen
unset ASR_MAX_WORKERS
export ASR_API_KEY='你的密钥'
nohup bash scripts/start_asr.sh >/dev/null 2>&1 &
```

每次启动会新建 `asr_server/logs/年-月-日/时-分-秒/`，控制台写进该目录的 `stdout.log`，不必再指到 `/tmp`。同一天再次启动是另一个时间目录，不会接着写上一次的文件。

启动成功后可见：

```bash
curl http://127.0.0.1:6006/health
```

关注字段：`model_loaded=true`、`api_key_required=true`、`queue_length`、`gpu_mem`、`disk`。

### 2.4 停止服务

找到进程后结束：

```bash
ps aux | grep 'python -m asr_server' | grep -v grep
kill <PID>
```

## 3. 公司内网：怎么调用

### 质量处理配置（1.8.0）

静音检查由调用方负责。服务端固定使用 `openai-whisper==20250625`，升级部署时先在原 Conda 环境执行 `pip install -r requirements.txt`，再重启服务。启动日志记录实际 Whisper 版本、模型、设备和质量阈值；每条任务日志记录实际解码参数。

以下环境变量在启动前设置，修改后重启生效：

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `ASR_LANGUAGE` | 空 | 自动识别语种，可固定 `en` / `zh` 等 |
| `ASR_STRICT_FILTER` | `true` | 严格后处理默认值，接受 `true` / `false` / `1` / `0`。上传表单的 `strict_filter` 可覆盖单个任务；省略、留空或只含空白时使用这里的值 |
| `ASR_MAX_ATTEMPTS` | `2` | 仅允许 1 或 2；第二次关闭前文上下文 |
| `ASR_SEGMENT_MAX_DURATION` | `29.0` | 单段时长达到此值触发结构异常 |
| `ASR_DURATION_TOLERANCE` | `0.5` | 结束越界和片段重叠容差，秒；轻微越界裁到音频末尾，明显重叠触发补救 |
| `ASR_TOTAL_DURATION_RATIO` | `1.15` | 片段时长总和相对音频时长的上限 |
| `ASR_REPETITION_COUNT` | `3` | 重复文本达到此次数且存在低置信度片段时触发补救 |
| `ASR_COMPRESSION_LIMIT` | `2.8` | 段内压缩比上限 |
| `ASR_NO_SPEECH_THRESHOLD` | `0.5` | 高无语音概率判定阈值 |
| `ASR_LOW_LOGPROB` | `-0.65` | 极低置信度删除阈值 |
| `ASR_AMBIGUOUS_LOGPROB` | `-0.5` | 存疑阈值；结合高无语音概率则删除 |

单段覆盖大部分音频不会独立触发异常；高置信度的真实重复口播保留。重识别后仍异常时逐段抢救并重新校验；选择过滤后可用片段较好的结果，优先通过质量检查的片段数量，再比较保留数量、删除数量和识别顺序，不直接选择字数最多的结果。

默认保持严格过滤。通用转写需要保留可疑文本时，上传表单传 `strict_filter=false` 或 `0`，或设置 `ASR_STRICT_FILTER=false` 后重启。表单值忽略大小写和两端空白；`true` 与 `1` 表示开启。不传这个字段、传空字符串或只传空白，都使用服务默认值，不会被当成关闭。其他取值在保存上传文件前拒绝，返回 `422`。关闭后，置信度、重复、压缩比和单段长度启发式只标记存疑，不触发删除或重识别；时间合法性、乱序、明显重叠和总时长检查始终执行。关闭开关只影响后处理，不关闭 Whisper 解码器原有的无语音判断等机制。可从 `/health` 的 `strict_filter_default` 查询服务默认值，从结果 `quality_analysis.strict_filter` 查询任务实际生效值。

当前仓库的 `client_example.py` 已支持该参数且完整保留响应字段。独立的 `video_edit_foreign` 项目还需配套修改远程适配器：接收质量指标和 `words`，移除“单段覆盖 80%”等旧启发式二次校验；否则仍可能丢失词级时间或回退 CPU。本仓库更新不会自动修改该项目。

本机无需 GPU 可运行 `python -m unittest discover -s tests -v`。AutoDL 升级后用正常短语音、真实重复口播、音乐音效混合、历史幻觉样本和长音频对照验证文本、拒绝原因与词级时间，再使用并发探测脚本重新评估路数；旧版两路／三路显存结论不能代替新版实测。

### 3.1 网络前提

内网 CPU 机器必须能访问 AutoDL 上的 HTTP 端口（常见方式：AutoDL 自定义服务/公网映射、专线、VPN、SSH 隧道等）。把最终可达地址记为：

```text
http://<主机或域名>:<端口>
```

例如：`http://region-xxx.autodl.com:xxxxx` 或内网穿透后的地址。以下用 `ASR_BASE_URL` 表示。

### 3.2 用示例客户端（推荐）

在**能访问 AutoDL** 的机器上：

```bash
export ASR_BASE_URL='http://<AutoDL可达地址>:6006'
export ASR_API_KEY='与服务器相同的密钥'

python client_example.py /path/to/audio_or_video.mp4 \
  --url "$ASR_BASE_URL" \
  --api-key "$ASR_API_KEY"
```

- 默认模式 `wait`：上传 → 拿 `task_id` → 轮询直到完成（流水线可当同步）。
- `--mode sync`：一条 HTTP 阻塞到结束（短任务调试；长队列/有网关超时时不推荐）。

### 3.3 在流水线代码里调用

```python
from client_example import transcribe_wait, get_asr

# 伪同步：拿到结果再进下一模块
out = transcribe_wait(
    audio_path,                          # 本机路径只写这一次，客户端会上传视频并记下路径
    base_url=ASR_BASE_URL,
    task_id="req_20261024_003",          # 流水线自己的唯一任务号
    api_key=ASR_API_KEY,
    poll_interval=1.5,
    timeout=3600,
)

text = out["result"]["text"]
segments = out["result"]["segments"]   # [{start_s, end_s, text}, ...]
language = out["result"]["language"]
task_id = out["task_id"]

# 24 小时内可再次查询（服务重启后也可从磁盘读）
again = get_asr(ASR_BASE_URL, task_id, api_key=ASR_API_KEY)

# 不再需要这条任务时立刻取消
from client_example import cancel_asr
cancel_asr(ASR_BASE_URL, task_id, api_key=ASR_API_KEY)
```

### 3.4 用 curl 手动试

```bash
# 提交。命令在持有视频的机器上执行。
# source_file_path 是记下来的路径文字，file 才是文件内容。路径使用正斜杠。
curl -X POST "$ASR_BASE_URL/v1/asr" \
  -H "X-API-Key: $ASR_API_KEY" \
  -F "task_id=req_20261024_003" \
  -F "source_file_path=D:/wjl/视频/国外测试视频/剪辑测试v4/airport_retracked_redacted.mp4" \
  -F "file=@D:/wjl/视频/国外测试视频/剪辑测试v4/airport_retracked_redacted.mp4"
# 刚受理时 status 为 2，status_name 为 queued。完整字段见接口文档。

# 查询
curl -H "X-API-Key: $ASR_API_KEY" \
  "$ASR_BASE_URL/v1/asr/<task_id>"

# 取消（马上返回）
curl -X POST -H "X-API-Key: $ASR_API_KEY" \
  "$ASR_BASE_URL/v1/asr/<task_id>/cancel"
```

完成时 `status` 为 `0`，`status_name` 为 `completed`，转写全文在 `result` 里。失败时 `status` 为 `1`，`status_name` 为 `failed`。时刻都是北京时间。字段和错误码以 `docs/接口文档.md` 为准。

## 4. 接口一览

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| `GET` | `/health` | 否 | 探活、队列、显存、磁盘 |
| `POST` | `/v1/asr` | 是 | 上传，立即返回 `task_id` |
| `GET` | `/v1/asr/{task_id}` | 是 | `status`：`0` 完成、`1` 失败、`2` 排队、`3` 转写中、`4` 已取消。对应 `status_name`：`completed` / `failed` / `queued` / `running` / `cancelled` |
| `POST` | `/v1/asr/{task_id}/cancel` | 是 | 立刻取消。正在跑的会停掉计算并重新加载模型 |
| `POST` | `/v1/asr/sync` | 是 | 阻塞到完成 |

鉴权方式（二选一）：

- 请求头：`X-API-Key: <密钥>`
- 或：`Authorization: Bearer <密钥>`

支持常见音视频后缀：`.wav` `.mp3` `.m4a` `.flac` `.ogg` `.mp4` `.mkv` `.webm` `.mov` 等。单文件默认上限 **500MB**。

生产环境默认关闭 `/docs`；需要调试可设 `ASR_ENABLE_DOCS=1` 后重启。

## 6. 日志与结果怎么看

### 6.1 日志

```bash
# 看今天有哪几次启动
ls /root/autodl-tmp/video_cut_forigen/asr_server/logs/$(date +%F)/
# 跟最新一次的业务日志。目录名是启动时刻，例如 18-22-05
tail -f /root/autodl-tmp/video_cut_forigen/asr_server/logs/$(date +%F)/18-22-05/asr.log
```

格式和 `asr_server/logs/日志格式示例.log` 一致。一行一件事，时刻是北京时间。

- 【开始】：某一路真正领到任务时写。含任务号、路号、来源路径、文件大小、音频时长、提交时刻、后面还排着几条、排队等了多久。
- 【结束】：完成、失败、取消都写这一行。后面是完整返回，完成时带转写全文和时间片段。
- 失败是错误级别。排队中取消没有【开始】，也没有路号。转写中取消两条都有。
- 模型加载、进程退出这类运行信息仍会写在同一个文件里，夹在任务行之间。

### 6.2 结果文件

```bash
ls /root/autodl-tmp/video_cut_forigen/asr_server/results/
cat /root/autodl-tmp/video_cut_forigen/asr_server/results/<task_id>.json
```

超过 24 小时会被后台清理。接口 `GET /v1/asr/{task_id}` 在内存没有时也会尝试读磁盘。

### 6.3 临时目录

```bash
ls /root/autodl-tmp/video_cut_forigen/asr_server/tmp/
```

正常应为空或仅有正在处理的文件。启动时会自动清残留。

## 7. 压测（测「能排多少 / 吞吐如何」）

在 AutoDL 本机或能访问服务的机器上：

```bash
cd /root/autodl-tmp/video_cut_forigen

# 先 8 路
python scripts/bench_asr.py \
  --file test_video/7b000bd63eda17d6b40136d295a0e221.mp4 \
  --n 8 \
  --url http://127.0.0.1:6006 \
  --api-key "$ASR_API_KEY"

# 再 80 / 100 路
python scripts/bench_asr.py --file test_video/7b000bd63eda17d6b40136d295a0e221.mp4 \
  --n 80 --url http://127.0.0.1:6006 --api-key "$ASR_API_KEY"
```

如何理解结果：

- **成功数 / 失败数**：队列与服务是否扛住提交量
- **吞吐（任务/秒）**：整体消化速度
- **单任务推理时长**：显卡真实算力
- **单任务墙钟**：含排队；80 路时墙钟会明显变长，属正常

这测的是「60 个任务能不能都排上队并逐条算完」，不是「显卡能不能同时算 60 路」。同时算几路见下一节。

2026-10-24 在本机（RTX 3080，20GB）用约 36 秒的样片测过 60 条：

- 成功 60，失败 0，总耗时 90.93 秒，大约每秒消化 0.66 条
- 单条推理平均 1.49 秒（最长 2.53 秒）。含排队的单条墙钟平均 48 秒，最长 91 秒
- 全部结束后模型仍在显存里，剩余大约 14737 MiB / 20480 MiB

60 条能接住，是因为它们在排队，不是因为显卡同时算了 60 路。

## 7.1 同时能算几路

服务实际开几路以 `asr_server/service.conf` 为准，默认 2。下面这条探测要先停掉语音服务，避免和服务自己的模型叠在一起：

```bash
python scripts/probe_parallel.py \
  --file test_video/7b000bd63eda17d6b40136d295a0e221.mp4
```

脚本会各加载一份模型，先测 1 路，再测 2 路同时转同一条样片，打印耗时和显存峰值。测完再启动服务。结论见本节末尾的实测记录（测完会写在下面）。

### 实测记录（2026-10-24，RTX 3080 20GB，同一条 36 秒样片）

测之前先停掉语音服务，避免服务自己的模型占着显存。

- 1 路：加载模型 16.67 秒，推理 2.51 秒，峰值显存 5316 MiB
- 2 路同时算：一起算完 2.73 秒（两条分别 2.41 秒、2.73 秒），峰值显存 10630 MiB / 20480 MiB
- 两条排队大约要 5 秒，所以 2 路这次更快，显存大约用掉一半，没有顶满

服务默认开 2 路。正在转写的任务一旦取消，只停掉它所在的那一路并重新加载这一路的模型（大约十几秒），另一路继续领队列里的任务。写成大于 3 时按 3 路启动。60 路同时算放不下：1 路连模型大约 5GB，60 路远超过 20GB。一次交来 60 条时，服务会全部排进队列，哪一路空闲就领下一条。

## 8. 常见问题

| 现象 | 可能原因 | 处理 |
|------|----------|------|
| `401 无效或缺失 API Key` | 内网未带 Key 或 Key 不一致 | 检查 `X-API-Key` / `ASR_API_KEY` |
| `409 任务已结束，无法取消` | 任务已经成功或失败 | 用查询结果，不要再取消 |
| `503 队列已满` | 排队超过上限 | 降本机提交速率，或调大 `ASR_MAX_QUEUE_SIZE` |
| `413 文件过大` | 超过上传上限 | 压缩/截断，或调大 `ASR_MAX_UPLOAD_BYTES` |
| `404 任务不存在或已过期` | 超过 24h，或 task_id 错误 | 重新提交；确认 ID |
| 转写报找不到 `ffmpeg` | PATH 未含 ffmpeg | 用 `scripts/start_asr.sh` 启动（已配 PATH） |
| 端口被占用 | 旧进程未关 | `ps` + `kill` 后再启 |
| 服务重启后任务丢了？ | 内存队列会丢；**已完成**的结果在磁盘留 24h | 用原 `task_id` 再查；未完成的需重提 |
| 内网连不上 AutoDL | 网络/端口未映射 | 先在 AutoDL 本机 `curl /health`，再查公网/映射 |

## 9. 上线检查清单

1. 已设置正式 `ASR_API_KEY`（不要用文档里的测试串长期上线）
2. `bash scripts/start_asr.sh` 启动成功，`/health` 正常
3. 内网用真实地址 + Key 跑通一条样片
4. 本次启动目录 `asr_server/logs/年-月-日/时-分-秒/asr.log` 里有【开始】和【结束】，【结束】里能看到转写全文
5. `asr_server/results/` 有对应 JSON；`tmp/` 用完为空

## 11. 文字识别（PP-OCRv6_small）

与语音服务并排，单独进程、单独环境、默认端口 `6008`。只加载一份检测模型和一份识别模型。一组图片在服务内部按批计算，不要为了并发再开第二份模型。

环境不装进 `whisper-turbo`。依赖见 `requirements-ocr.txt`，飞桨 GPU 版要从 CUDA 12 的官方索引安装。本机环境目录是 `/root/autodl-tmp/envs/ocr-pp`。推理模型在 `/root/autodl-tmp/models/ocr`，引擎是静态图 `paddle_static`。

批大小写在 `ocr_server/service.conf`。2026-10-28 用样片抽出的一帧、复制成相同分辨率的 32 张和 100 张测过：

- 100 张逐张（检测 1、识别 1）约 8.7 秒
- 检测 4、识别 16 约 6.0 秒，是这次扫描里最快的一档
- 检测 8、识别 32 约 7.7 秒，没有更快
- 单独跑时显存高水位大约 2.2GB，出现在把检测批加到 16 的时候。选用的 4 和 16 远低于 18GB

因此默认 `det_batch = 4`、`rec_batch = 16`。识别时只把宽度相差不超过百分之一的文字行放进同一批，避免长短行补齐后多出或少一个空格。改完需要重启文字识别服务。

单次请求最多 32 张。一个视频若有上百张图，调用方按每组最多 32 张分开提交，每组使用自己的任务号。

调用方式和语音相同：`POST /v1/ocr` 提交后立刻返回，`GET /v1/ocr/{task_id}` 查询，`POST /v1/ocr/{task_id}/cancel` 取消，`POST /v1/ocr/sync` 阻塞到结束。任务号由调用方传入，规则与语音一致。结果默认保留 24 小时。

取消排队中的任务会马上把它摘掉。正在识别的任务，取消接口马上返回；当前已经送进模型的这一小批算完后停下，半截结果丢掉。模型保持加载，后面排队的组继续算。

启动：

```bash
cd /root/autodl-tmp/video_cut_forigen
export ASR_API_KEY='与语音服务相同的密钥'
bash scripts/start_ocr.sh
```

默认监听：`0.0.0.0:6008`。

后台运行（关掉终端后服务仍在）。启动脚本会把控制台写进当次日志目录，这里把输出丢掉即可：

```bash
cd /root/autodl-tmp/video_cut_forigen
export ASR_API_KEY='与语音服务相同的密钥'
nohup bash scripts/start_ocr.sh >/dev/null 2>&1 &
```

每次启动会新建 `ocr_server/logs/年-月-日/时-分-秒/`，控制台写进该目录的 `stdout.log`，不必再指到 `/tmp`。同一天再次启动是另一个时间目录，不会接着写上一次的文件。

启动成功后可见：

```bash
curl http://127.0.0.1:6008/health
```

健康检查里看 `model_loaded`、`det_batch`、`rec_batch`、`queue_length`、`gpu_mem`。

关闭。先按进程名找到文字识别服务，再结束对应进程号：

```bash
ps aux | grep 'python -m ocr_server' | grep -v grep
kill <PID>
```

确认已经退出时，再执行一次 `curl http://127.0.0.1:6008/health`，连不上即已关闭。语音服务进程名是 `python -m asr_server`，两条命令互不影响。

调用示例（默认提交后轮询，先打印任务号，便于另开一次调用取消）：

```bash
export OCR_BASE_URL='http://127.0.0.1:6008'
python ocr_client_example.py frame_001.jpg frame_002.jpg \
  --source 'D:/视频/a.mp4' \
  --url "$OCR_BASE_URL" --api-key "$ASR_API_KEY"
```

已经切好的文字行用 `--mode rec_only`。要一次请求阻塞到结束，加上 `--call sync`。取消：

```python
from ocr_client_example import cancel_ocr
cancel_ocr("http://127.0.0.1:6008", "任务号", api_key="密钥")
```

批大小探测（先停掉语音，测完再启动语音）：
